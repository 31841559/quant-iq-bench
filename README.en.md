# quant-iq-bench

**How much IQ does quantization actually cost?** This benchmark answers exactly that.

Every question is generated by a seeded script, every ground-truth answer is computed
by the script itself, and every answer is scored programmatically. No public question
bank is involved — so "the model has memorized this item" is ruled out by construction.

```bash
python -m bench.scoring --self-check
python -m bench.gen --suite charops --n 50 --seed 20261109 --out q.json
BENCH_BASE_URL=http://127.0.0.1:8080/v1 BENCH_MODEL=your-model \
  python -m bench.run --questions q.json --out r.json --thinking
python -m bench.report --run r.json --ref other.json
```

Zero dependencies (stdlib only), Python ≥ 3.9. Works with any OpenAI-compatible
`/v1/chat/completions` endpoint.

---

## Why not MMLU-style leaderboards

1. **Contamination.** Classic items are on the internet. High scores may just be recall.
2. **Granularity.** One aggregate number hides *which* capability degraded.
3. **Loose scoring.** LLM-as-judge error can exceed the effect you are trying to measure.

This suite inverts all three: questions are generated on the spot, answers are computed
by code, and scoring is either exact match or a programmatic constraint check. Change
the seed and the whole suite is new.

## Three task families

| Suite | What it probes | Scoring |
|---|---|---|
| `charops` | Character-level precision: reversal, positional swaps, insert/delete, case flips | Exact string match |
| `arith` | Multi-step numeric reasoning: discounts, tax, weighted averages, FX fees | Numeric tolerance < 0.005 |
| `constraint` | Instruction following: exact character counts, JSON keys, separators, no Markdown | Programmatic validation |

`charops` is the hardest family and the one most likely to expose precision failures
(dropped steps, lost characters). `arith` is the control group — if a model fails there,
the problem is your serving configuration, not quantization. In the 100-item run,
`constraint` turned out to be the sharpest discriminator.

Ambiguity is removed on purpose: "swap all **lowercase** letters b and c (lowercase only)"
rather than "swap all b and c", because positional operations shift indices and a model
that reads "swap b and c" case-insensitively is being reasonable, not wrong.

## Results

Same machine (Apple M5 Ultra, 256 GB unified memory), one model family:
local 3.0-bit quantized build vs the cloud flagship.

**90 standard items** (combinatorics, CRT, date arithmetic, modular exponentiation,
truth-tellers, table extraction):

| Model | Accuracy |
|---|---|
| Local 3.0 bpw (224 GB resident) | **90/90** |
| Cloud flagship | **90/90** |

**40 hard character-transformation items** (7 steps, 16–22 chars, index drift):

| Model | Accuracy |
|---|---|
| Local 3.0 bpw | **35/40** |
| Previous local 8-bit build | 23/34 (overlapping items) |

**100 mixed items** (50 char + 25 arithmetic + 25 constraint, seed 20261109, both sides blind):

| Suite | Local 3.0 bpw | Reference (blind) |
|---|---|---|
| `charops` | 43/50 | 44/50 |
| `arith` | 25/25 | 25/25 |
| `constraint` | **21/25** | 25/25 |
| **Total** | **89/100** | **94/100** |

11 discordant pairs, **McNemar exact test p = 0.227 — still not significant**.

**This table overturns the smaller one below, and it is the one to believe.** At n=24 the
charops gap was 3 items (5/8 vs 7/8); at 50 charops items it mostly vanishes (43 vs 44).
The persistent weakness moved: **output-format compliance**. Three of the four failures are
the same bug — asked for one item per line, it emits `海南、广东、广西` joined by ideographic commas.

**24 fresh mixed items** (8 char + 8 arithmetic + 8 constraint):

| Model | Char | Arith | Constraint | Total |
|---|---|---|---|---|
| Local 3.0 bpw | 5/8 | 8/8 | 7/8 | **20/24** |
| Cloud flagship | 7/8 | 8/8 | 8/8 | **23/24** |

A 3-item gap, but only 4 discordant pairs — **McNemar exact test p ≈ 0.63, i.e. not
significant**. `bench/report.py --ref` computes this for you.

> **Provenance of the reference column:** no cloud API key was configured, so the
> "cloud flagship" numbers come from the assistant model answering **blind** — questions
> only, no answers, then compared against script-computed ground truth. It is not a
> separately executed API batch; treat it as an approximation, not a strict control.

**Takeaway:** quantization costs almost nothing on tasks that can be *computed*, and at
n=50 character-level work is roughly at parity too (43 vs 44). The weakness that survives
scaling is **output-format compliance** — ask for one item per line and you get ideographic
commas; ask for a JSON array and you get `460300`.

See [`docs/findings.md`](docs/findings.md) (Chinese) for the full analysis.

## Four pitfalls, all encoded in the client

1. **Thinking is off by default** on many local stacks. Without `enable_thinking` the
   model skips reasoning and guesses — two-digit arithmetic starts failing. Enabled by default.
2. **`HTTP_PROXY` hijacks LAN requests** and returns a fake 502. The client bypasses the
   proxy explicitly and keeps a `curl` fallback transport for sandboxes that only allow it.
3. **Small `max_tokens` makes the answer vanish**: the model hits the cap mid-thought and
   returns empty `content`. Defaults to 8192, with recovery from `reasoning_content`.
4. **A scorer that doesn't match the output style measures itself.** Hence `--self-check`
   (33 cases) — run it before touching scoring logic.

## Layout

```
bench/
  client.py        OpenAI-compatible client (thinking / json_schema / proxy bypass / retry / empty-answer recovery)
  scoring.py       Scorer + McNemar exact test + 33 self-check cases
  gen.py           Question generator CLI (does not echo answers by default, for blind runs)
  run.py           Runner CLI (resume, concurrency, per-item persistence)
  report.py        Report (per-family breakdown, failure detail, paired significance)
  suites/          charops / arith / constraint
data/              question sets (with and without answers) and run results
docs/findings.md   What is a configuration bug and what is a real weakness
```

## Caveats

- `temperature=0` **does not guarantee determinism** on every stack. Compare runs from the
  same batch, never mix rounds.
- Sample size bounds your claim. 3 items out of 24 is noise; you need 100+ for an interval.
- Only reasoning and instruction following are measured. No knowledge, no long context, no multi-turn.
- Character-task accuracy depends on prompt quality. If a model gives a *reasonable other
  reading*, fix the prompt instead of blaming the model.
