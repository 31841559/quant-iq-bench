# quant-iq-bench

**量化到底让模型变傻了多少？** 这套基准只回答这一个问题。

全部题目由脚本 + 随机种子生成，标准答案由脚本独立计算，判分 100% 程序化。
不引用任何公开题库，所以「模型背过这道题」这条干扰项被排除掉了。

```bash
python -m bench.scoring --self-check          # 33 条判分用例，先确认尺子是准的
python -m bench.gen --suite charops --n 50 --seed 20261109 --out q.json
BENCH_BASE_URL=http://127.0.0.1:8080/v1 BENCH_MODEL=your-model \
  python -m bench.run --questions q.json --out r.json --thinking
python -m bench.report --run r.json --ref other.json
```

零依赖，只要 Python ≥ 3.9。兼容任何 OpenAI 风格的 `/v1/chat/completions`。

## 为什么不用 MMLU 那类榜单

三个理由，都很实际：

1. **污染**。经典题在网上，模型见过。分数高不代表会推理。
2. **粒度粗**。聚合到一个数字，看不出「哪一类能力掉了」。
3. **判分软**。主观题靠模型打分，误差比要测的差距还大。

这套基准反过来：题目现场生成、答案脚本算、判分要么精确相等要么程序化校验。
随机种子一变，题目全新 —— 模型不可能背过。

## 三个题型

| 题型 | 测什么 | 判分方式 |
|---|---|---|
| `charops` 字符多步变换 | 逐字符精确执行：反转、位置交换、插入删除、大小写 | 字符串精确相等 |
| `arith` 链条算术 | 多步数值推理与精度保持（折扣/税/加权/汇率） | 数值误差 < 0.005 |
| `constraint` 指令硬约束 | 听话程度：字数、JSON 字段、分隔符、禁 Markdown | 程序化校验 |

`charops` 是最难的题型，最容易暴露精度问题（漏步骤、丢字符）。
`arith` 是对照组：如果模型连这里都崩，说明是服务配置问题，不是量化问题。
100 题实测里，真正把两边拉开的是 `constraint`。

题面强制消歧：

- 写「交换所有**小写**字母 b 和 c（只换小写的）」，不写「交换所有 b 和 c」
- 写「按**当时的**字符串从 1 开始数」，因为位置操作会让下标漂移
- 自动过滤空操作过多的题（避免「五步里三步不改变字符串」）

## 实测数据

同一台机器（Apple M5 Ultra，256 GB 统一内存），同一个模型家族的量化包 vs 云端旗舰。

**标准题 90 道**（排列组合、中国剩余定理、日期差、幂取模、真假话、表格抽取）：

| 模型 | 正确率 |
|---|---|
| 本地 3.0 bpw（224 GB 常驻） | **90/90** |
| 云端旗舰 | **90/90** |

**字符多步变换**（40 道困难档：7 步、16–22 字符、含位置漂移）：

| 模型 | 正确率 |
|---|---|
| 本地 3.0 bpw | **35/40** |
| 上一代本地 8 bit | 23/34（同题重叠部分） |

**100 道混合题**（50 字符 + 25 算术 + 25 指令，seed 20261109，双方盲测）：

| 题型 | 本地 3.0 bpw | 参照（盲答） |
|---|---|---|
| `charops` 字符多步变换 | 43/50 | 44/50 |
| `arith` 链条算术 | 25/25 | 25/25 |
| `constraint` 指令硬约束 | **21/25** | 25/25 |
| **合计** | **89/100** | **94/100** |

不一致配对 11 组，**McNemar 精确检验 p = 0.227，仍不显著**。

**这张表推翻了上一张小表的结论，而它才是对的。** 24 题时字符题差 3 道（5/8 vs 7/8），
扩到 50 道之后差距基本消失（43 vs 44）。真正稳定存在的短板换了一个位置 ——
**指令格式遵循**：4 道失败里有 3 道是同一个毛病，要求「每行一个」，它输出
`海南、广东、广西`（顿号连写）。

> 这就是为什么要扩样本量。24 题里的 3 题差距，大半是噪声。

**24 题小样本**（8 字符 + 8 算术 + 8 约束）：

| 模型 | 字符 | 算术 | 约束 | 合计 |
|---|---|---|---|---|
| 本地 3.0 bpw | 5/8 | 8/8 | 7/8 | **20/24** |
| 云端旗舰 | 7/8 | 8/8 | 8/8 | **23/24** |

差 3 题，但配对不一致只有 4 组，**McNemar 精确检验 p ≈ 0.63 —— 统计上不显著**。
`bench/report.py` 会把这个数直接算出来，不需要你手算。

> **参照侧是怎么来的**：没有配云端 API key，所以「云端旗舰」那一列是
> 由当前会话的模型（同一家族）**盲答**产生 —— 先出题、只看题面、不看答案，
> 答完再和脚本算出的标准答案对照。原始答卷在
> `data/results/20261109-reference-official.json`。
> 它不是一次 API 批量调用，这一点必须说清楚，别当成严格同条件对照。

### 一句话总结

> 量化在「算得出来」的任务上几乎没有损失（25/25 对 25/25，90 题对 90 题）；
> 在「一个字符一个字符抠」的活上，量化模型和强模型基本打平（43 对 44）。
> 真正稳定的短板是**格式遵循** —— 要求每行一个，它给你顿号连写；
> 要求只输出 JSON，它给你一个数字。

详细分析见 [`docs/findings.md`](docs/findings.md)。

## 四个坑（都写进代码了）

跑这套东西之前，先看这四条，能省几个小时：

1. **思考模式默认是关的**。不开 `enable_thinking`，模型会跳过推理直接猜，
   表现为「两位数加法也算错」。`Client` 默认开启。
2. **`HTTP_PROXY` 会劫持内网请求**，返回 502 假象。`Client` 显式绕过代理，
   并保留 curl 作为 fallback transport。
3. **`max_tokens` 太小会让答案蒸发**：思考没结束就撞上限，`content` 返回空。
   默认给 8192，并且 content 空时从 `reasoning` 兜底抽取。
4. **判分器不适配输出风格时，你测的是判分器**。所以有 `--self-check`。

## 项目结构

```
bench/
  client.py        OpenAI 兼容客户端（thinking / json_schema / 代理绕过 / 重试 / 空答案兜底）
  scoring.py       判分器 + McNemar 检验 + 33 条自检用例
  gen.py           出题 CLI（默认不回显答案，便于盲测）
  run.py           跑测 CLI（断点续跑、并发、逐题落盘）
  report.py        汇总报告（题型分项、失败明细、配对显著性）
  suites/
    charops.py     字符多步变换
    arith.py       链条算术
    constraint.py  指令硬约束
data/
  questions/       题库（含答案 + 不含答案的盲测版）
  results/         跑测结果与盲答参照
docs/
  findings.md      实测结论：哪些是配置问题，哪些是真短板
```

## 复现与对照

想比较两个模型（或两个量化版本），最稳的做法是**同一轮数据、同一套题**：

```bash
# A 侧
BENCH_MODEL=model-a python -m bench.run --questions q.json --out a.json
# B 侧
BENCH_MODEL=model-b python -m bench.run --questions q.json --out b.json
# 配对比较（会算 McNemar）
python -m bench.report --run b.json --ref a.json
```

注意 `temperature=0` **不保证确定性** —— 同一个 prompt 两次跑结果可能不同。
所以别把不同轮次的结果混在一起算，要么同一轮跑完，要么重跑。

## 局限

- **字符题的绝对正确率依赖题面质量**。写得再清楚，也挡不住模型给出「合理的另一种理解」。
  遇到这种情况，改题面，别怪模型。
- **样本量决定结论强度**。24 题差 3 题不显著，100 题以上才谈得上区间。
- **只测推理与指令遵循**。不测知识、不测长文、不测多轮。
- **算术题的两位小数**对判分容差敏感（当前 0.005），自检里覆盖了这类边界。
