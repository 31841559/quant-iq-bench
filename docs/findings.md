# 实测结论

这份文档记录的是跑这套基准时真正学到的东西，不是跑分表。跑分表在 `README.md`，
这里说的是**为什么会出现那些分**。

---

## 一、最反直觉的一条：大多数「模型变笨」是配置问题

同一台机器、同一个模型权重，只改一处参数，成绩从 23/25 变成 25/25。
下面五个坑，每一个都会让人误判成「量化把模型搞傻了」。

### 坑 1：思考模式默认是关的

本地推理栈（mlx-serve / 部分 vLLM 配置 / 某些 chat template）默认不启用 thinking。
没有 `reasoning_content` 通道时，模型被模板约束成「直接给答案」，
于是它真的跳过推理去猜：

```
问：13 的平方减 7 的立方加 100 等于多少？只输出整数。
答：106          ← 正确是 -74
再问一次：-194    ← 同一个 prompt，两次不同的错法
```

加上一行参数就恢复正常：

```python
payload["chat_template_kwargs"] = {"enable_thinking": True}
```

```
reasoning_content: 计算：13 的平方 - 7 的立方 + 100 = 169 - 343 + 100 = -74
content: -74
```

**判断方法**：如果模型在「两位数加减」这种题上都错，先别怀疑模型，
先确认请求里有没有开 thinking。

### 坑 2：`HTTP_PROXY` 把内网请求劫持成 502

本机设了代理（跑 VLESS 的人基本都有），urllib 默认 `trust_env=True`，
访问 `192.168.x.x` 时也被塞进代理，返回 502。

现象极其误导人：**curl 能通，Python 不通**，看起来像代码写错了或者服务挂了。

修复：

```python
opener = urllib.request.build_opener(urllib.request.ProxyHandler({}))
```

`bench/client.py` 里还保留了 curl 子进程作为 fallback —— 因为某些沙箱按进程放行网络，
Python socket 直连会被拦，而 curl 放行。

### 坑 3：`max_tokens` 太小时，答案直接蒸发

长思考题会把预算烧在 reasoning 上，`finish_reason=stop` 但 `content=""`，
答案卡在 reasoning 里出不来。

```
d09  8192 tok 耗尽 → content 空 → 耗时 80.6 秒
d37  8192 tok 耗尽 → content 空 → 耗时 146.6 秒
```

把上限放宽到 8192（默认）之后，原来「答错」的两题全对。
**这类失败不是智力问题，是预算问题。**

`Client.chat()` 里做了三重兜底：content 空 → 从 reasoning 末行捞 → 仍为空则重试。

### 坑 4：判分器不适配输出风格时，你测的是判分器

这条最隐蔽，也最容易得出错误结论：

| 模型实际输出 | 我的旧判分 | 真相 |
|---|---|---|
| `\boxed{\dfrac{99}{100}}` | 判错 | 答对了 |
| `## 答案：B 说真话` | 判错 | 答对了 |
| `DB4`（十六进制） | 按整数解析失败 | 答对了 |
| `海南、广东、广西` | 判对（但要求每行一个） | 答错了 |

所以 `bench/scoring.py` 里所有能程序化校验的都不做字符串相等，
并且自带 `python -m bench.scoring --self-check`（33 条用例）。
**改判分逻辑前先跑自检**，否则你会在无意中放宽或收紧标准。

### 坑 5：题面歧义会被算成「答错」

「交换所有 b 和 c」——模型理解成不分大小写，把转大写后的 B/C 也换了。
这个理解比我的标准答案更自然。**题目错了，不是模型错了。**

现在的题面一律写「交换所有**小写**字母 b 和 c（只换小写的）」「按**当时的**字符串从 1 开始数」。
写不清楚就别测。

## 二、真正修不掉的短板：逐字符精确执行

开思考模式、给足 token、加 schema 约束之后，剩下的差距集中在**两类**任务上：
需要逐字符数、改、反转的活，以及需要精确遵守输出格式的活。
前者在 100 题盲测里其实被打平了，后者才是稳定的短板（见本节末尾的修正）。

典型失败长这样（推理全对，执行错位）：

```
标准：CAEADEAAC
输出：CAEADAEAC     ← 把中间的 EA 写成 AE
```

而且它是**确定性**的 —— 同一个 prompt 重试 100 次，错在同一个位置。
这说明不是采样抖动，是这类操作的固有精度问题。

实测数据：

| 题集 | 本地 3bpw | 官方旗舰 |
|---|---|---|
| 标准题（90 道：排列组合、中国剩余定理、日期、幂取模、真假话） | 90/90 | 90/90 |
| 字符多步变换（40 道困难档：7 步、16–22 字符、含位置漂移） | 35/40 | 未测 |
| 全新混合（24 道：8 字符 + 8 算术 + 8 约束） | 20/24 | 23/24 |
| **100 道混合（50 字符 + 25 算术 + 25 指令）** | **89/100** | **94/100**（盲答） |

**算术类是零差距**：8/8 对 8/8，25/25 对 25/25。

### 但是——扩到 100 题之后，结论要改

上面 24 题那一行显示字符题差 3 道（5/8 对 7/8）。把样本量加到 50 道字符题之后：

| 题型 | 本地 3bpw | 盲答参照 |
|---|---|---|
| 字符多步变换（50 道） | 43/50 = 86% | 44/50 = 88% |
| 链条算术（25 道） | 25/25 | 25/25 |
| 指令硬约束（25 道） | **21/25 = 84%** | 25/25 = 100% |

**字符题的差距基本消失了**（差 1 道），24 题里的那 3 道差距大半是噪声。
真正稳定存在的是**格式遵循**：4 道失败里有 3 道是同一个毛病 ——
要求「每行一个」，它输出 `海南、广东、广西`。

第 4 道更离谱：要求「以 JSON 数组输出三个地级市」，它思考了 3522 字符，
最后输出了 `460300`。完全跑偏，但 token 消耗只有 1085 —— 说明它不是想不出来，
是思考路径整个走歪了。

这条修正本身就是方法论的证据：**n=24 的结论不可靠，n=100 才勉强能说话。**

正确做法不是换更大的模型，而是**别让模型心算**：

让模型写 Python，交给 subprocess 执行。同一批字符串题，心算 1/3，代码路线 3/3。
字符题的心算路径 token 消耗是普通题的 15 倍，而且随时可能跑满 90 秒还没结果。

## 三、量化到底损失了什么

用同一个模型家族做对照：本地 3.0bit 量化包（224 GB 常驻）vs 云端旗舰。

| 维度 | 结论 |
|---|---|
| 可计算题型 | **无损失**（90/90 对 90/90） |
| 逐字符操作 | 100 题盲测下基本打平（43 对 44），早期 40 题困难档有损失（35/40） |
| 格式遵循 | **稳定有差距**（21/25 对 25/25），且不随样本量消失 |
| 长链收尾 | 3bit 版更容易把 token 烧在自我纠缠上 |
| 速度 | 85 tok/s，但单题只消耗 ~214 token，比 8bit 版更快出结果 |

有意思的是：3bit 版**思考更省**（英文思考、平均 345 字符），
所以在简单题上反而比高比特版本更快出答案。量化损失的不是「思考意愿」，是「尾部精度」。

## 四、方法学上的三个诚实说明

### 1. 样本量决定你能说什么

24 题里差 3 题，不一致配对只有 4 组，McNemar 精确检验 p ≈ 0.63。
**这个差距在统计上不显著**，严谨说法是「有迹象，不足以定论」。
`bench/report.py --ref` 会直接算给你看，别拿百分比当结论。

### 2. `temperature=0` 不保证确定性

同一个 prompt 在同一台机器上跑两次，结果可以不同（实测过）。
所以**跨轮比较必须用同一轮的数据**，别把昨天的结果和今天的混着算。

### 3. 污染控制

所有题目由脚本 + 随机种子生成，标准答案由脚本独立计算，
生成器默认**不回显答案**（`--show-answers` 才打印），
这样可以让人或另一个模型先盲答、再对照 —— 双方都没背过答案。

即便如此，字符类题目的失败里有一部分是**我自己也犯的错**（第一次盲答 50 道字符题错了 6 道：
漏做步骤、删错位置、没注意「复制成两份后交换只影响第一份」）。
所以别把「模型答错」直接等价于「模型不行」—— 先确认人能不能答对。
